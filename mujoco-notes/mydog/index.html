01从 CAD 到 MJCF（自建机械狗）

目标：把 SolidWorks 装配体变成 MuJoCo/MJX 能训的模型。这条路踩了很多坑，记录下来。

1. 路线

SolidWorks 装配体(.SLDASM)
  → sw2robot / URDF 导出
  → 修正 URDF（坐标系、碰撞、关节）
  → MJCF（MuJoCo XML）
  → 简化（串联腿）用于 MJX 训练

2. 两个模型版本（按用途）

版本 文件 用途 特点
四杆闭环 dog_mjcf/dog.xml MuJoCo 本地看/仿真 真四杆：hip/knee 驱动 + rod/shank 被动 + 膝盖销 equality×4
串联简化 dog_mjcf_simple/dog_simple.xml MJX/RL 训练 每腿 hip+knee 直驱，无闭环

为什么分两版：MJX 对 equality 闭环不稳（体重一压容易折叠），所以训练用串联简化版；四杆版更真实，用来本地验证运动学。 两版同几何/同质量/同网格，总质量 ~6.0kg。

3. 常见导出问题 & 修复

  1. 网格碰撞：CAD 导出的三角网格直接做碰撞，MJX 容易炸/OOM → 改成基本体碰撞（box/capsule/sphere）。
  2. 积分器：implicitfast 在 MJX 不稳 → 改 Euler。
  3. contype/conaffinity 位掩码：2 & 1 == 0 → 腿不碰地、直接穿地。统一改成 contype=1 的碰撞体、地板 conaffinity=1。
  4. 中文路径：MuJoCo 在 Windows 打不开中文路径 → 用英文副本目录。
  5. 坐标系不统一：各零件导出后局部坐标系不一致（后面镜像修复的根源，见 02 篇）。

4. XML 关键设置（本项目）

xml<compiler angle="radian" autolimits="true"/>
<option timestep="0.004" integrator="Euler"/>
<!-- 视觉网格：只做外观 -->
<default><geom type="mesh" density="0" contype="0" conaffinity="0"/></default>
<!-- 碰撞体：单独给 contype=1 -->
<geom name="thigh_col1" type="capsule" contype="1" conaffinity="0" .../>
  • 视觉网格 density=0, contype=0 → 不参与质量/碰撞（后面“镜像只改视觉不影响物理”就靠这个）。
  • 每腿结构：L{i}_thigh（含 hip joint）→ L{i}_shank（含 knee joint）→ 脚。
  • home keyframe 存参考站姿（四脚等高的解）。

5. 关节与执行器

  • 每腿 2 个 hinge（hip、knee）；共 8 个执行器 m_hip_L1..4、m_knee_L1..4。
  • 骨盆（base）用 freejoint（6 DOF）。
  • qpos = 7(free) + 8 = 15；qvel = 6 + 8 = 14。

6. 生成脚本（若需重建）

scripts/build_dog_model_v2.py（四杆）、scripts/build_dog_simple.py（串联）、scripts/level_stance2.py（调平求解）。

7. 教训

  • CAD 装配姿态 ≠ 物理正确姿态：手拼装配体常没对齐，导出只是忠实还原（四脚高低不一、髋偏移）。
  • MJX 对复杂约束（equality/闭环）宽容度低 → 训练模型要“能省则省”。
  • 模型是后面所有 RL 的地基，地基歪了，奖励怎么调都白搭（见 03/04 篇）。

02模型问题与镜像对称修复（重点）

自建狗模型最坑的一段：左右不对称 + 视觉网格炸开。这里记录诊断、数学、脚本、验证全过程，可直接复用。

1. 现象

  • 四脚高度不一致（0.131 / 0.100 / 0.064 / 0.034 m），L4 髋横向偏 3.2cm；
  • 用同一套"镜像"逻辑修完，右腿视觉网格飞出去（thigh_mid 顶点跑到 x=-0.61 / z=0.66，腿"炸开"）；
  • 视觉上"模型显示不对"，但碰撞/关节其实对。

2. 诊断

用 scripts/mydog_symmetry_check.py 在世界坐标下比较 L1↔mirror(L3)、L2↔mirror(L4) 的关节锚点/脚： - 关节/碰撞体：hip 完全对称、knee/foot 有偏差（最大 0.076m）； - 进一步用网格顶点比较（更严格的镜像距离）：右腿网格对左腿镜像误差 10~90mm → 原始模型的网格本身就没镜像好。

3. 关键认知：反射不能复用同一份网格

把左腿"镜像"到右腿，几何变换是关于 x-z 平面反射（y→-y）： - 位置 (x,y,z) → (x,-y,z)； - 四元数 (w,x,y,z) → (w,-x,y,-z)（即 M·R·M，M=diag(1,-1,1)）； - fromto 两端 y 取反；关节 axis 的 y 取反； - 惯性 fullinertia 的 Ixy、Iyz 取反。

但反射矩阵 det(M)=-1，不是旋转。 想用同一份未镜像的 STL 得到镜像件，数学上不可能——第一次我只反射了变换、没镜像网格，结果每个网格被"转到错误朝向"，腿就炸开了（thigh_mid 顶点甩到 z=0.66）。 → 正确做法：同时镜像网格资产。

4. 解决方案（两个脚本）

(a) scripts/mirror_mydog_meshes.py —— 生成镜像 STL

对腿用到的 7 个网格 knee_conn/motor/thigh_in/thigh_mid/thigh_out/shank/foot： - 顶点 y 反射 y→-y； - 交换三角形绕序（保证法线朝外，否则渲染黑/反面）； - 写成 *_R.stl（二进制 STL，格式：80 字节头 + uint32 数量 + 每三角 50 字节）。

(b) scripts/mirror_mydog_legs.py —— 重建右腿

  • 取 L1_thigh、L2_thigh 子树，做上面的反射；
  • 命名改写 L1→L3、L2→L4（col1→col3 等）；网格引用换成 *_R.stl；
  • 在 <asset> 登记镜像网格；
  • 修 home keyframe：右腿关节轴翻成 -y 后，为与左腿对称，L3=-L1、L4=-L2。

白盒推导：设左腿网格点 V、变换 (R1,t1)；镜像后世界点 = M(R1 V + t1)。 取 V' = M V（镜像网格）、t3 = M t1、R3 = M R1 M，则 R3 V' + t3 = M R1 V + M t1 完全相等 → 真镜像。 （这正是"镜像网格 + 反射变换"组合生效的原因。）

5. 验证（mydog_symmetry_check.py）

  • 关节/碰撞体镜像：0.00000 m；
  • 网格逐顶点镜像距离：10~90mm → 0.00mm；
  • 四脚等高（z≈0.001，在 qpos0 和 home 两种姿态下都对称）；
  • 渲染 ASCII 复核：无飞出/悬空部件。

6. 重要副作用：物理没变

  • 视觉网格是 contype=0, density=0 → 不参与碰撞、不贡献质量；
  • 所以"修视觉网格"不改变动力学 → 镜像修复前训好的 ONNX（物理相同）仍然有效，不用重训。

7. 教训

  • 先验证网格，不只验证关节：很多"对称"只差在视觉网格上。
  • 反射 ≠ 旋转：涉及网格/惯性的镜像，必须连网格一起镜像。
  • 修模型前先备份：mydog_simple.xml.bak_before_symmetry。
  • 建模时最好在 CAD 就"参考坐标系统一/镜像装配"，能省掉这一整套修修补补。

03自建狗 RL 环境与训练结果

在自建狗上跑 MJX + Brax PPO，扩了 stand / walk 两个任务。这一篇记录环境、命令、结果，以及一次“奖励被刷”的教训。

1. 环境代码结构

mjplay/mujoco_playground/_src/locomotion/mydog/ | 文件 | 作用 | |---|---| | mydog_constants.py | 模型路径、body/sensor 名 | | base.py | MyDogEnv 基类（PD、观测、termination 等） | | stand.py | MyDogStandFlatTerrain（站立） | | walk.py | MyDogWalkFlatTerrain（直走） | | randomize.py | 域随机化（摩擦/质量/质心/armature…） | | xmls/mydog_simple.xml | 模型（串联腿，见 01/02 篇） |

注册：locomotion/__init__.py + config/locomotion_params.py。

2. 观测 / 动作

任务 obs 动作
Stand 30 = gyro(3)+gravity(3)+ (q−q_home)(8)+qvel(8)+last_act(8) 8 关节力矩增量
Walk 35 = 上面 + command(3) + 步态时钟 sin/cos(2) 8

env 内 PD：target = q_home + act*0.1，tau = Kp*(target−q) − Kd*qd，clamp ±12。

3. 训练命令

bashcd ~/mujoco_ws/go2_rl/mjplay
python3 -u learning/train_jax_ppo.py --env_name=MyDogWalkFlatTerrain \
  --num_timesteps=80000000 --num_envs=2048 --num_evals=10 \
  --domain_randomization=True --use_tb=True --num_videos=0 --suffix=mydog_walk_xxx

自建狗比 Go2 慢（~96k–200k 步/分），一条 60–80M 约数小时。

4. Stand 结果

运行 设置 结果
mydog_stand_v3 DR reward ~14.2，height 284，ep_len 300
mydog_stand_sym 对称模型/no-DR reward 14.38（~10M 后平台），四脚等高

→ 对称化后站立训练没有变差，说明镜像改造没伤性能。

5. Walk 结果（一路实验）

运行 说明 reward 备注
mydog_walk_cont2 基础直走 22.5 步态是 bound
mydog_trot2 加步态时钟+feet_clearance — gait 匹配↑，tracking 掉
walk_sym 对称模型 28.7 会走，L3 偏弱
walk_sym2 加“方差对称奖励” 32.8 退化：后腿拖地、不前进
walk_sym3 改“每脚达标奖励” 39.5 指标好看，但仍拖后腿（见 04 篇）

6. 关键教训：奖励被“刷”了

walk_sym2 的对称奖励设计有漏洞：

foot_symmetry = -var(各脚最近落地抬脚峰值)
  • 直觉：让四脚抬得一样高 → 对称。
  • 漏洞：脚不落地就不更新峰值、全部保持 0 → 方差=0 → 满分。策略于是干脆都不抬脚（或只抬前腿），reward 反而更高。结果：后腿拖地、机身不前进。
  • 验证：在训练环境（MJX）里也一样拖后腿（不是 sim gap）。

修法（walk_sym3）：换成“每只脚必须达标才给分”

foot_lift = Σ_f clip(最近摆动抬脚峰值 / 目标高度, 0, 1)   # 不抬的脚得 0
## 抬脚瞬间把该脚峰值清零（防“抬一次就吃老本”）
  • 好处：站着/少抬脚拿不到分，不可刷。
  • 结果：foot_lift 从 401→632、clearance 惩罚 −328→−17，指标确实在往“四脚都抬”走。
  • 但：最终逐脚验证仍然后腿弱（见 04 篇结论）——指标改善 ≠ 真走起来。

7. 导出 ONNX

bashcd ~/mujoco_ws/go2_rl
sed 's/Go2JoystickFlatTerrain/MyDogWalkFlatTerrain/' scripts/export_go2_onnx.py > /tmp/export_walk.py
python3 /tmp/export_walk.py --ckpt mjplay/logs/<run>/checkpoints --out policies/mydog_walk_xxx.onnx

查看：python3 scripts/onnx_mydog_walk_viewer.py --onnx policies/mydog_walk_xxx.onnx

8. 小结

  • 自建狗能训起来（stand 很稳），但 walk 的“四条腿均匀迈步”很难。
  • 奖励一定要防“退化解”（少做=高分）。
  • reward 高不等于行为对，必须逐脚/逐行为验证（见 04 篇）。

04结论：MJX↔MuJoCo gap 与模型瓶颈

这一篇是整个自建狗系列的“诚实总结”：我们到底卡在哪、为什么、下一步。

1. MJX↔MuJoCo gap（真实存在）

同一份 walk_sym 策略（ONNX/checkpoint），在两个环境里表现差别巨大：

指标 MJX（训练环境） MuJoCo（普通仿真）
机身前进（6s） +0.558 m +0.059 m
四脚抬脚 都能抬（后腿 15mm+） 后腿几乎拖地（6mm）
  • 说明：在 MJX 里能走的策略，到 MuJoCo 明显退化。这就是 sim-to-sim gap（更别说 sim-to-real）。
  • 原因方向：接触/摩擦/求解器差异、MJX 与 MuJoCo 的数值实现不同。

2. 更糟的是：训练里就有“拖后腿”

  • walk_sym2 / walk_sym3 在训练环境（MJX）里也拖两条后腿（L1/L3 抬 6–8mm）、机身几乎不前进。
  • 所以：后期的退化不是 gap，是策略本身没学对（奖励被刷/局部最优）。
  • 对比：早期 walk_sym 在 MJX 里确实走了 +0.558m（虽然后腿 L3 偏弱），是“相对最好”的。

3. 那到底是模型问题还是训练问题？

  • 模型能抬腿：手写一个开环 trot，四脚都能抬 100–160mm（说明关节/几何没有物理性缺陷）。
  • 但干净稳定的 trot 很难：我们试了 1. 关节正弦（knee 反相）→ 向后退着飞、前腿蹬后腿拖； 2. 关节正弦（knee 同相）→ 能走但像“蹦”（腿在扑腾）； 3. 足端轨迹 + 腿部 IK → IK 发散/机身塌陷（手写实现也不稳）。
  • RL 和手写都卡在同一处 → 瓶颈在模型/动力学本身，不只是奖励：
  • 腿是串联 2-DOF、几何较怪（大腿朝后下、小腿朝前下）；
  • 脚掌很小、机身 ~6kg 相对腿偏重；
  • 缺少能稳定支撑/推动的足端接触，容易“扑腾/塌”。

4. 结论

  • 能站（stand 很稳），能训（RL 跑得起来），但“四条腿均匀迈步的稳定 trot”做不出来（RL 与我手写都失败）。
  • 这不是“再调调奖励/多训一会儿”能解决的——要动模型。

5. 下一步方向（任选其一或多选）

  1. 改模型（最根治）： - 调腿长/脚掌大小/质心/关节限位/摩擦；让足端能稳定支撑与推动； - 或参考成熟四足（如 Go2）的腿型/质量分布重构。
  2. 换更标准的四足模型：先在 Go2/Anymal 上把步态跑通，再迁移回自建狗。
  3. 用经典控制器：足端轨迹 + 正确的 IK + VMC 平衡层（本项目 go2_mpc 方向，但需要补稳定平衡层）。
  4. 暂时接受：walk_sym 是相对最好的一版（MJX 能走），先用于展示/文档，走路问题留作后续。

6. 最重要的方法论教训

  • reward 高 ≠ 行为对：一定逐脚/逐行为验证（本项目多次被 reward 指标“骗”）。
  • 先分清 gap 还是训练失败：在训练环境里单独测一遍（我们就是靠这个确认 sym2/sym3 是训练问题）。
  • 模型是地基：地基（几何/质量/接触）不改进，奖励和算法都是空中楼阁。
  • 保留备份与可回退：ONNX、checkpoint、模型 .bak 都留着，实验失败能回去。

这一段经历比“成功”更有价值：它把 RL 里“奖励设计、reward hacking、sim gap、模型重要性”全踩了一遍。
